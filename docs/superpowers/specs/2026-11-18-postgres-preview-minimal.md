# PostgreSQL 미리보기 최소판

사용자가 2026-11-18 PostgreSQL 미리보기 최소판을 요청했다. 이 문서에는 같은 날 실행한 [SP22 실측](../../spikes/SP22.md)을 반영했다.

## 범위

- **한다:** PostgreSQL 18 한 서버(원본과 샌드박스가 같은 서버)에서 INSERT·UPDATE·DELETE 미리보기. 원인 트리(직접·FK 연쇄·트리거), 행 비교, 문장별 결과.
- **안 한다:** [원본에 적용], 프로시저·함수 호출(`CALL`, `DO`), Split(원격 원본), 설정 화면에서 PostgreSQL 연결 저장(환경 변수로만), 롤백 뒤 남은 변경 검사.
- 화면은 지금 것을 그대로 쓴다. 엔진이 PostgreSQL이면 [원본에 적용]을 끄고 이유를 보이며, 편집기 방언을 PostgreSQL로 바꾼다.

## 경계(코드 조사 2026-11-18)

미리보기 흐름(`PreviewPipeline`), 변경 묶기(`ChangeCollector`), 원인 귀속(`CausalResolver`), 저장소·API·화면은 DB와 무관하다. PostgreSQL 구현은 새 프로젝트 `src/DbRipple.Postgres`(Npgsql)에 두고 아래 자리에 꽂는다.

| 자리 | SQL Server | PostgreSQL 최소판 |
|---|---|---|
| `ISandboxManager` | BACKUP/RESTORE, DB 스냅샷 | `CREATE DATABASE 샌드박스 TEMPLATE 원본`, 감사 설치, 카탈로그·지문·매니페스트 |
| `IBatchAnalyzer` | ScriptDom | 문장 나누기(따옴표·`$태그$`·주석 인식) + 첫 낱말로 허용/거부 + 대상 테이블 |
| `ITriggerAnalyzer` 결과 | ScriptDom 정적 분석 | 트리거 함수 본문(`prosrc`)에서 INSERT INTO·UPDATE·DELETE FROM 대상을 찾는 보수적 분석, `EXECUTE`가 있으면 동적 SQL |
| `IPreviewExecutor` | T-SQL 실행 봉투 | Npgsql 트랜잭션 봉투, 감사 읽기, 감사 이미지로 최종 차이, ROLLBACK |
| `IColumnTypeSource` | sys.columns | `format_type` |
| `IApplyService` | ApplyService | 지원 안 함(501) |
| 조립 | `CreateEngine` | 엔진 설정이 `Postgres`면 위 구현으로 조립 |

`IBatchAnalyzer`는 지금 DI 싱글턴이라 `/api/analyze`가 늘 SQL Server 분석기를 쓴다. 엔진 묶음(`Engine`)에 분석기를 넣고 DI는 엔진에서 꺼내게 바꾼다.

## 결정

1. **샌드박스 복제는 TEMPLATE.** 원본에 다른 연결이 있으면 PostgreSQL이 복제를 거절한다(SQLSTATE 55006). 도구는 원본 세션을 유지한다. 새로 고침 요청은 202를 반환하고, 복제가 실패하면 상태 API는 `error`를 반환한다. SQLSTATE 55006은 psql에서 확인했다. 기준 시각은 복제가 끝난 시각이다. 기준 비교용 스냅샷 DB는 만들지 않는다(PostgreSQL은 DB 사이 조회가 안 된다). 새로 고침은 `DROP DATABASE 샌드박스 WITH (FORCE)`(PostgreSQL 13 이상) 뒤 다시 복제한다. 지우는 것은 **도구가 만든 DB뿐**이다: 복제 직후 DB 주석(`COMMENT ON DATABASE`)으로 소유 표시를 남기고, 같은 이름의 DB가 이미 있는데 그 주석이 없으면 지우지 않고 오류로 끝낸다. 시스템 DB 이름(`postgres`, `template0/1`)과 원본과 같은 이름은 받지 않는다. 매니페스트·기준 시각·원본 이름은 샌드박스의 `dbr_audit.meta`에 둔다(Host를 다시 켜면 거기서 읽는다).
2. **감사 수집은 문장 단위 AFTER 트리거 + 전이 테이블.** 테이블마다 INSERT·UPDATE·DELETE 트리거 3개(`zzz_dbr_audit_i|u|d`, `REFERENCING ... TABLE`). PostgreSQL은 같은 종류 트리거를 이름순으로 부르므로 `zzz_` 접두로 마지막에 돈다. 이름이 더 뒤인 사용자 트리거가 있으면 매니페스트에 NONE으로 적는다. 감사 저장소는 샌드박스의 `dbr_audit` 스키마(순번 시퀀스, 헤더, 행 이미지, meta). 감사 함수는 `SECURITY DEFINER`(미리보기 역할은 감사 스키마에 권한이 없다). 깊이는 `pg_trigger_depth()`. 키는 수집기와 같은 규칙(`TableKey.Choose`: PK → NOT NULL UNIQUE 인덱스 ID 순 → ROW). 파티션 테이블·파티션은 최소판에서 제외(매니페스트 excluded). 직접 문장과 FK 연쇄 모두 0행 묶음의 헤더를 남긴다. SP22에서 빈 FK 묶음의 깊이는 그 연쇄를 시작한 문장과 같았다. 중첩된 0행 문장도 문장 단위 사용자 트리거의 쓰기 문맥이 될 수 있으므로 깊이와 관계없이 보존한다. **이미지 상한(2026-11-19 변경):** 상한은 한 미리보기에서 FULL로 쓴 이미지 수가 상한(기본 100,000)을 넘지 않게 하는 것이다. 실행기는 트랜잭션 시작 때 `set_config('dbr.image_cap', 상한, true)`를 둔다. 이 트랜잭션 GUC는 **"남은 FULL 예산"**이다. 감사 함수는 **발동마다** 헤더를 쓰기 전에 이번 발동 이미지 수 n(`dbr_new` + `dbr_old` 행 수)을 예산과 비교한다(`dbr_audit.full_for`, O(1)이고 감사 표를 세지 않음). n > 예산이면 그 발동부터 KEYS(`row_json` NULL, `key_json`은 그대로)로 쓰고 `set_config('dbr.image_mode', 'KEYS', true)`로 뒤 발동도 KEYS가 되게 한다. n ≤ 예산이면(같음 포함) `set_config('dbr.image_cap', 예산 − n, true)`로 예산을 줄이고 FULL로 쓴다. 0행 발동은 모드도 예산도 바꾸지 않는다. 예산 GUC가 없거나 빈 값이면(옛 실행기) 판정하지 않고 FULL, 숫자가 아니면 형 변환 오류 대신 KEYS로 닫는다. 헤더 `image_mode`에는 실제로 쓴 모드를 적는다. 그래서 부모 10만 행 DELETE 같은 **한 문장 안에서도** 상한을 지킨다(전에는 문장이 끝난 뒤에만 보고 다음 문장부터 바꿔, 2026-11-19 클라우드 측정에서 한 문장이 FULL 이미지 50만 개를 남겼다). 판정 결과는 "지금까지 FULL + n > 상한"과 같다. 같은 날 처음 구현한 헤더 합 방식은 발동마다 헤더를 세어 1행짜리 발동이 많으면 비용이 발동 수의 제곱이 되어 예산 방식으로 바꿨다. 감사 함수 안의 `set_config(…, true)`는 함수의 `SET search_path` 절과 다른 변수라 함수가 끝나도 트랜잭션 끝까지 남는다. 사용자 트리거의 예외 블록이 되돌린 발동은 GUC 변경도 함께 되돌려져 예산과 기록이 맞는다. 감사 저장소 표 구조는 그대로이고 함수 본문만 바뀌었으므로, 이미 만든 샌드박스는 새로 고침 전까지 옛 함수라 지금처럼 문장 사이에서만 KEYS로 바뀐다.
3. **실행 봉투.** 전용 연결(풀링 끔) `BEGIN` → 문장마다 `SET LOCAL ROLE dbr_preview` → 실행·행 수 → `RESET ROLE` → 경계(그 트랜잭션 안 헤더 순번 최댓값) → 감사 읽기 → 최종 차이 → `ROLLBACK`. 오류가 나면 PostgreSQL 트랜잭션은 중단되므로 그 문장 뒤는 not_run, 수집·최종 차이는 비운다. PostgreSQL 트리거 함수는 COMMIT할 수 없어 롤백 뒤 남은 변경 검사는 하지 않는다(시퀀스 값 소비는 남는다). 오류 문맥에 사용자 PL/pgSQL 함수가 있으면 `trigger_blocked`, `dbr_audit.*` 함수면 도구 오류(`failed`), 그 밖은 `failed`. SQLSTATE는 메시지 앞에 붙이고 오류 번호는 0. **주의(2026-11-19 정정):** `SET ROLE NONE`·`RESET ROLE`(`set_config('role', 'none', …)`)은 모든 사용자에게 허용되어 session user(연결 계정, 샌드박스 소유자)로 돌아가므로, superuser가 아닌 연결 계정이어도 `SET LOCAL ROLE`은 보안 경계가 아니다. 역할 경계는 분석기 거부 목록(문장 `SET`·`RESET`, 문장 안 `set_config`, 결정 7)에만 기대며, 사용자 함수·트리거 본문 안까지는 막지 못한다. 근본 해결은 사용자 문장을 실행하는 연결의 session user를 다른 역할의 구성원이 아닌 LOGIN 미리보기 역할로 바꾸는 것이다(후속 과제). 연결 계정은 superuser가 아닌 계정(CREATEDB·CREATEROLE)을 권장한다(superuser면 사용자 함수 안에서 더 많은 일을 할 수 있다). 실행기는 트랜잭션 시작 때 `standard_conforming_strings = on`을 `SET LOCAL`과 같게 둔다(문장 나누기는 일반 `'…'` 안의 백슬래시를 이스케이프로 보지 않으므로 서버도 같게 강제, 2026-11-19). 카탈로그 읽기 SQL은 백슬래시 없이 `LIKE … ESCAPE '!'`로 써서 이 설정과 무관하다.
4. **최종 차이는 감사 이미지로(순수 계산 `ImageNetDiff`).** 묶음마다 DELETED 이미지를 −1, INSERTED 이미지를 +1로 (키, 행 문자열)마다 더한다. 전이 테이블은 그 문장이 지우고 넣은 행 그대로라 **더하는 순서와 상관없이 "최종 − 처음"이 남는다**(트리거 안에서 같은 행을 다시 고쳐 기록 순서가 실제 순서와 달라도 맞음). 키마다 남은 −1·+1이 하나씩이면 UPDATED, 하나만이면 DELETED/INSERTED, 키 없는 테이블은 다중집합. 이미지 상한을 넘어 KEYS 묶음이 하나라도 생긴 테이블은 이 방법을 못 쓰므로, 테이블 전체를 재조회로 넘겨 before는 트랜잭션 밖 새 연결(확정된 기준선), after는 트랜잭션 안에서 감사에 나온 키만 다시 읽는다(키 없는 테이블은 전체 다중집합 비교, 느린 길). 2026-11-19부터 상한은 발동 단위(남은 FULL 예산, 결정 2)라 한 문장 안에서도 같은 테이블에 FULL·KEYS 묶음이 섞일 수 있다. 재조회 키는 그 테이블의 FULL·KEYS 묶음 이미지 모두에서 모으므로(감사 함수는 FULL에서도 `key_json`을 남김) 빠지는 키가 없다(`ImageNetDiff.Compute`, `PgPreviewExecutor.RereadKeys`). 실행기는 문장 뒤 그 문장 범위에 KEYS 헤더가 있으면(옛 함수는 누적 FULL 이미지 수 > 상한이면) 그 뒤 모드를 KEYS로 적고 결과를 `truncated`로 둔다. `truncated`는 "상한 때문에 KEYS로 기록한 묶음이 하나라도 있음"이고 `imageCount`는 FULL로 쓴 이미지 수다(결과 JSON 모양은 그대로). 감사 밖 테이블·롤백 뒤 남은 변경은 보지 못한다. 이 한계는 분석 경고(`WARN_PG_MINIMAL_SCOPE`)로 매 미리보기에 남긴다.
5. **FK 연쇄의 깊이와 순서.** PostgreSQL 18.7에서 RI 트리거의 자식 DML은 부모 행마다 실행됐고, SP22의 전이 테이블은 같은 연쇄의 변경을 자식 테이블별 한 묶음으로 모았다. FK 감사 헤더는 연쇄를 시작한 문장과 같은 깊이에서 그 문장 뒤에 기록됐다. 사용자 트리거가 명시적으로 실행한 문장의 감사 헤더는 한 단계 더 깊고 SP22의 트리거 사슬에서는 후위였다. 실행기는 관측 깊이와 순번을 그대로 전달한다. 기존 원인 판정(FkJudge)은 같은 문장 안의 FK 키와 깊이로 연쇄를 귀속하며, 수집기의 후위 괄호는 사용자 트리거 문맥에 쓴다. 이 순서는 [SP22](../../spikes/SP22.md)의 관측 범위에 해당한다.
6. **값 문자열.** 감사는 `to_jsonb` 뒤 `->>`로 열마다 문자열(NULL은 JSON null)을 담는다. 계약 규칙(모든 값은 문자열, NULL은 null)과 같고, 같은 함수라 같은 값은 같은 문자열이다. 숫자는 jsonb 원문, 불리언 `true`/`false`, 시각은 ISO(`T` 구분).
7. **문장 분석(`PgSqlLexer` + `PgBatchAnalyzer`).** 문장 나누기는 `'…'`(E'…' 포함), `"…"`, `$태그$…$태그$`, `--`, 중첩 `/* */`를 인식하고 닫히지 않으면 `REJECT_PARSE_ERROR`. 허용: `INSERT INTO`, `UPDATE [ONLY]`, `DELETE FROM [ONLY]`. 스키마를 생략한 대상은 `public`에서만 찾는다(샌드박스는 원본 DB의 search_path 설정을 물려받지 않음). 거부 규칙 ID는 기존 것을 다시 쓴다: `REJECT_TRUNCATE`, `REJECT_MERGE`, `REJECT_EXEC`(CALL·DO·EXECUTE), `REJECT_TRANSACTION_CONTROL`, `REJECT_SET_OPTION`(SET·RESET), `REJECT_DDL`, `REJECT_BULK_INSERT`(COPY), `REJECT_SELECT_INTO`, `REJECT_ADMIN_COMMAND`(VACUUM·NOTIFY·LISTEN 등 문장 + `set_config`·백엔드 종료·`pg_notify`·`pg_sleep`·advisory lock 전부(`pg_advisory*`·`pg_try_advisory*`)·SQL 문자열을 실행하는 함수(`*_to_xml*` 전부, `ts_stat`, `ts_rewrite`, tablefunc의 `crosstab*`·`connectby`)·복제 슬롯·원점·복원 지점·논리 메시지(`pg_create_*`, `pg_copy_*`, `pg_drop_replication_slot`, `pg_replication_slot_*`, `pg_replication_origin_*`, `pg_logical_*`)·WAL·백업(`pg_switch_wal`, `pg_wal_replay_*`, `pg_backup_*`, `pg_promote`)·통계 초기화(`pg_stat_reset*`)·서버 로그(`pg_log_backend_memory_contexts`, `pg_log_standby_snapshot`)), `REJECT_EXTERNAL_ROWSET`(`dblink*`·pgsql-http(`http`, `http_*`)·서버 파일 읽기·목록·쓰기(`pg_read_*`, `pg_ls_*`, `pg_stat_file`, `pg_current_logfile`, `pg_file_*`)·`lo_import/export`; 거부 목록은 2026-11-19 보안 검토로 보강했고 접두는 위 `*` 표기, INSERT 대상 테이블 이름 뒤 열 목록 괄호는 함수 호출로 보지 않는다), `REJECT_NOT_ALLOWED`(SELECT·WITH 등), `REJECT_TARGET_NOT_USER_TABLE`(없음·시스템·파티션), `REJECT_CAPTURE_STORE`(dbr_audit). 2026-11-19: 거부 목록 함수(`REJECT_ADMIN_COMMAND`·`REJECT_EXTERNAL_ROWSET`)는 따옴표 이름(`"set_config"(…)`, `"pg_catalog"."set_config"(…)`)도 본다. 따옴표 이름은 PostgreSQL처럼 대소문자를 그대로 비교하고(`"SET_CONFIG"`는 다른 함수), 따옴표 없는 이름은 소문자로 접는다. 렉서가 풀지 않는 유니코드 이스케이프 식별자 `U&"…"`는 이름 검사를 피할 수 있어 문장째 `REJECT_NOT_ALLOWED`다(문법 오류가 아니라 받지 않는 구문, `U&'…'` 문자열은 그대로). 트리거 본문의 외부 부작용 검사도 따옴표 이름과 pgsql-http 단독 `http(…)`를 잡고 `U&"…"`가 있으면 외부 부작용으로 둔다(관리 함수 목록은 트리거 본문 검사에 아직 없다). 도달하는 트리거(직접 대상 + FK 연쇄 + 트리거 쓰기 대상)에 외부 부작용(`pg_notify`·dblink·COPY·신뢰하지 않는 언어 등)이 있으면 `REJECT_TRIGGER_EXTERNAL_EFFECT`, 동적·모름은 `WARN_TRIGGER_DYNAMIC_SQL`, 감사 순서 NONE은 `WARN_AUDIT_NOT_LAST`. 새 규칙은 경고 하나 `WARN_PG_MINIMAL_SCOPE`(스크립트마다 한 번).
8. **트리거 분석은 보수적으로(`PgTriggerAnalyzer`).** 주석·문자열을 지운 함수 본문에서 INSERT INTO·UPDATE … SET·DELETE FROM 대상을 찾는다. 동적 SQL(`EXECUTE`), plpgsql·sql 밖의 언어, 이름을 풀 수 없는 대상이 있으면 `WriteTargetsUnknown`. 신뢰하지 않는 언어(plpython3u 등)는 외부 부작용으로 둔다. 트리거 원인은 지금처럼 `inferred`.
9. **지문.** 한 서버라 원본·샌드박스 지문은 늘 같다(`FingerprintMatch = true`). 값: 서버 버전, "PostgreSQL", 주버전, DB 정렬(나머지 SQL Server 항목은 고정값).
10. **객체 ID.** PostgreSQL oid(uint32)를 int로 넣는다. 2^31을 넘으면 기준선 구축을 실패로 끝낸다(사용자 객체 oid는 보통 16384부터라 실제로는 거의 없음).
11. **엔진 선택.** `DbRipple:Engine` = `SqlServer`(기본) | `Postgres`, 환경 변수 `DBRIPPLE_ENGINE`이 우선. PostgreSQL 서버 연결은 `DBRIPPLE_PG_CONNECTION`(관리용 DB `postgres`에 붙는 Npgsql 연결 문자열). 원본·샌드박스 DB 이름은 SQL Server 기본값(AW_Origin)과 섞이지 않게 `DbRipple:Pg:OriginDb`(필수, 환경 변수 `DbRipple__Pg__OriginDb`)·`DbRipple:Pg:SandboxDb`(기본 `원본_dbr_sandbox`), 소문자·숫자·밑줄만. 선택: `Pg:PreviewRole`(기본 `dbr_preview`), `Pg:CommandTimeoutSeconds`(기본 60). 설정 화면에서 SQL Server 연결을 저장하면 그 묶음으로 바뀐다.
12. **API·화면.** `SandboxStatus.engine`(PostgreSQL이면 `"postgres"`, SQL Server는 필드 없음 — 기존 JSON 모양 유지)을 더한다. 문장 분석기는 엔진 묶음(`Engine.Analyzer`)에서 꺼낸다. [적용] API는 501. 화면은 엔진이 postgres면 편집기 문법을 PostgreSQL(기본 스키마 public)로, [원본에 적용]은 "PostgreSQL 최소판은 [적용]을 지원하지 않습니다" 한 줄로 끈다. 2026-11-18 추가: `SandboxStatus.lastError`(error 상태일 때만, 비밀번호 가림)로 새로 고침 실패 이유(예 원본 연결 때문의 55006)를 보내고, 상단 샌드박스 상태 칩을 열면 "실패 이유"로 보인다(SQL Server도 같음).
