# SP18 — 원본 스냅샷 실패의 오류 번호

**상태: 실행 완료(2026-11-16). 통과(s3 성공, 사유별 번호 기록).** 판정 H1·H2·H4·H5 PASS, **H3 FAIL(5133이 아니라 5123, Linux는 없는 폴더도 OS 오류 5)**, **H6 FAIL(CREATE ANY DATABASE만으로는 1817)**. H6에서 **제품 결함**을 찾았다: [적용]의 검증 모드 사전 결정은 CREATE DATABASE 권한만 보므로, CREATE ANY DATABASE는 있고 원본 DB의 db_owner가 아닌 로그인은 "스냅샷 가능"으로 판정된 뒤 1817로 실패하고 동의해도 KEYSET_HASH로 갈 수 없다(아래 "제품 수준 재현"). 로그 `spikes/logs/sp18-*.log`(제품 수준 재현의 API 응답은 `sp18-40-api-repro.log`), `logs/home-test/2026-11-16/sp18/`. 실행 중 보조 스크립트 3개(`sp18_20`·`sp18_30`·`sp18_39`)를 더했다. 2026-11-13 준비 때는 정적 검토만 했다(ScriptDom TSql170 파싱 오류 0).

## 목적

[적용]의 검증은 원본에 데이터베이스 스냅샷을 만들어 하는 정확 검증이 기본이고, 못 만들면 약한 검증(KEYSET_HASH, 사용자 동의)으로 내려간다. 2026-11-13 결정은 "**예상 밖 스냅샷 오류는 조용히 강등하지 않고 오류로 보인다**"이다. 그러려면 "스냅샷을 만들 수 없는 정상적인 사유(권한 없음, 에디션·경로 제약)"와 "예상 밖 오류"를 오류 번호로 가를 수 있어야 한다. 실제로 어떤 번호가 나는지 잰다.
- 제한 로그인(`CREATE ANY DATABASE` 없음)의 스냅샷 시도는 어떤 번호인가.
- 잘못된 경로(없는 폴더, 쓸 수 없는 폴더)는 어떤 번호인가.
- 이름 충돌(이미 있는 DB 이름), 없는 원본 DB는 어떤 번호인가.
- 권한을 주면(`CREATE ANY DATABASE`) 제한 로그인이 성공하는가(최소 권한 목록에 이 권한을 더하면 정확 검증이 되는가).

연결: SP17(원본 모사 컨테이너·제한 로그인), SP21(약한 검증), 제품의 `OriginSnapshotSuffix`(기본 `_pre`)·`ApplySteps`의 스냅샷 오류 분류.

## 방법

`spikes/sql/sp18_10_snapshot_errors.sql`을 원본 모사 컨테이너(2022)에서 sa로 실행한다. 원본 CascadeLab의 데이터 파일 논리 이름으로 `CREATE DATABASE CascadeLab_sp18 ON (…) AS SNAPSHOT OF CascadeLab`을 만들어 시나리오별로 TRY/CATCH로 오류 번호·심각도·상태·메시지를 기록한다(제한 로그인 시나리오는 `EXECUTE AS LOGIN`).

| 시나리오 | 누구로 | 무엇을 |
|---|---|---|
| s1 | 제한 로그인 | 정상 경로 |
| s2 | sa | 없는 폴더(`/no/such/dir/`) |
| s3 | sa | 정상 경로(기준: 성공해야 함) |
| s4 | sa | 이미 있는 DB 이름(`CascadeLab_RT`)으로 |
| s5 | sa | 없는 원본(`NoSuchDb_sp18`) |
| s6 | sa | 있지도 않은 파일(`bogus_sp18`)을 더해서 |
| s7 | sa | 루트 폴더(`/`, mssql 사용자가 쓸 수 없음) |
| s9 | 제한 로그인 + `CREATE ANY DATABASE` 임시 부여 | 정상 경로(끝에서 반드시 REVOKE) |

성공한 스냅샷은 바로 지운다. 끝의 확인 쿼리가 남은 스냅샷 DB 0개, 남은 임시 권한 0개를 보인다.

### 확인한 사실 / 추정 / 설계 반영

증거 범위: DB 실측(컨테이너 SQL Server 2022 CU28, Linux) + 제품 수준 재현은 Host 개발 모드 API(Split, 샌드박스 2025 CU10). Windows의 SQL Server(없는 폴더가 OS 오류 3으로 나올 수 있음), Standard·Express 에디션, sysadmin이 아닌 서버 역할 dbcreator는 재지 않았다.

확인한 사실:
- 원본 스냅샷 생성 실패 번호는 사유별로 갈린다: 권한 262(CREATE DATABASE 없음)·1817(원본 DB 소유·db_owner·CONTROL 없음), 이름 충돌 1801, 파일 경로 5123(Linux에서는 없는 폴더·쓸 수 없는 폴더 모두 OS 오류 5), 없는 원본 911, 없는 파일 이름 5014.
- 스냅샷을 만들려면 **CREATE DATABASE 권한(CREATE ANY DATABASE 또는 master의 CREATE DATABASE)과 원본 DB의 CONTROL(db_owner 역할·DB 소유자 포함)이 둘 다** 필요하다(sysadmin은 둘 다 가진다). 하나만 있으면 262 또는 1817이다.
- 제품 결함(재현됨): 검증 모드 사전 결정이 CREATE DATABASE 권한만 본다. CREATE ANY DATABASE만 있는 로그인은 SNAPSHOT_NETDIFF로 정해진 뒤 1817 오류로 끝나고, `allowKeysetVerification`이 있어도 KEYSET_HASH로 바뀌지 않는다. 원본은 바뀌지 않는다(실행 전 실패).

추정: dbcreator 서버 역할도 CREATE ANY DATABASE와 같이 동작할 것이다(재지 않음). 1817은 권한 변경이 검사와 생성 사이에 일어나는 경합에서만 남는다(검사를 고친 뒤).

"스냅샷 실패 = 오류, KEYSET은 명시 동의" 결정에 대한 묶음(제안):
- 실행 전 검사로 "스냅샷 불가(정상 사유 → 약한 검증 선택지 제시)": CREATE DATABASE 권한 없음(262가 날 경우), **원본 DB CONTROL 없음(1817이 날 경우, 검사 추가 필요)**, FILESTREAM·메모리 최적화 파일 그룹. 이 경우만 `WEAK_VERIFICATION_NOT_ACCEPTED` → 동의 → KEYSET_HASH.
- 실행 중 생성 실패는 지금처럼 모두 error(조용한 강등 없음). 메시지 분류: 262·1817 = 권한(검사 뒤 권한이 바뀜), 1801·50001 = 이름 충돌(서버 설정), 5123 = 스냅샷 파일 경로·디스크(서버 데이터 폴더), 911·5014 = 예상 밖.

설계 반영(정정 필요):
- SP18 가설 H3의 기대 5133 → 실측 5123(Linux). H6의 기대 "성공" → 실측 1817.
- 최소 권한 목록: 정확 검증(SNAPSHOT_NETDIFF)을 원하면 원본 로그인에 CREATE ANY DATABASE **와** 원본 DB CONTROL(또는 db_owner)이 필요하다. 이는 SP17의 최소 권한(db_backupoperator + DML)보다 훨씬 넓고 원본 DB에 DDL 권한까지 주므로, 기본은 KEYSET_HASH(동의)로 두는 것이 맞다.
- 제품 수정 제안: `OriginSnapshot.CapabilitySql`(`ApplySteps.cs:614-619`)에 `HAS_PERMS_BY_NAME(N'<원본>', N'DATABASE', N'CONTROL')`을 더하고 `Decide`(`ApplySteps.cs:622-629`)가 둘 다 있어야 `CanSnapshot = true`로, 없으면 이유 "원본 DB에 CONTROL(db_owner) 권한이 없음(스냅샷은 DB 소유자·db_owner·sysadmin만)"을 내게 한다. `PermissionErrors`(`ApplySteps.cs:608`)에 1817을 더한다. 검증 테스트: `Decide(canCreateDatabase: true, hasDbControl: false, …)` → `CanSnapshot = false`(단위), `ApplyServiceFlowTests`에 이 능력 값으로 동의 없음 → `WEAK_VERIFICATION_NOT_ACCEPTED`, 동의 → KEYSET_HASH 커밋, DB 테스트로 CREATE ANY DATABASE만 준 로그인의 `CheckSnapshotCapabilityAsync`가 false, CONTROL을 더하면 true이고 `CreateSnapshotAsync`가 Created.
