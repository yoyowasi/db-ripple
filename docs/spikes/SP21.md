# SP21 — KEYSET_HASH(약한 검증)의 검출력과 비용

**상태: 실행 완료(2026-11-16).** A: H2·H3 PASS, **H1 FAIL(m2 두 행 맞바꾸기를 CHECKSUM_AGG가 못 잡음, 정정 필요)**. B: **PASS**(`rolled_back_mismatch`, `OUTSIDE_TABLE_CHANGED` sp21.Y, 원본 불변). C: **FAIL(제품 결함)** — 데이터 손상·무한 대기는 없지만, 잠긴 행이 미리보기 테이블에 있으면 드리프트 확인 단계의 1222가 처리되지 않아 [적용] API가 **HTTP 500 "서버 내부 오류입니다"**로 끝난다(미리보기 밖 테이블만 잠긴 경우는 `status = error`로 처리됨). D: AW 해시 한 번 p50 약 0.46초(71테이블 76만 행), CascadeLab 약 4ms. 로그 `spikes/logs/sp21-*.log`(B·C API 응답과 C의 Host 콘솔 오류 부분은 `sp21-50-api.log`), `logs/home-test/2026-11-16/sp21/`. 실행 중 `sp21_40` 시간 측정을 고치고(음수 ms) 보조 스크립트 `sp21_31`을 더했다. 2026-11-13 준비 때는 정적 검토만 했다(ScriptDom TSql170 파싱 오류 0).

## 목적

원본 스냅샷을 만들 수 없을 때 [적용]은 약한 검증(`verification.mode = KEYSET_HASH`, 동의 필요)을 쓴다: 미리보기에 없던 테이블의 `COUNT_BIG(*)`·`CHECKSUM_AGG(BINARY_CHECKSUM(*))`가 바뀌면 `OUTSIDE_TABLE_CHANGED`로 막고 롤백한다. 이 장치가 실제로 얼마나 잡고 얼마나 놓치는지, 비용은 얼마인지 잰다.
1. **검출력(해시 수준)**: 같은 행 수로 값만 바뀌는 변경, 두 행 값 맞바꾸기, 바꿨다 되돌리기, 대소문자만 바꾸기, xml 열만 바꾸기를 해시가 알아채는가. 알려진 틈(비교 불가 형식)이 어디인가.
2. **검출력(제품 수준)**: 원본에만 있는 트리거가 미리보기 밖 테이블을 행 수 그대로 UPDATE할 때 [적용]이 `OUTSIDE_TABLE_CHANGED`로 막고 롤백하는가.
3. **동시 세션 쓰기**: [적용] 중 다른 세션이 같은 행을 잡고 있으면 어떻게 실패하는가(롤백 쪽 실패, LOCK_TIMEOUT).
4. **트랜잭션 안 시간**: 모든 사용자 테이블의 해시를 한 번 계산하는 데 걸리는 시간(적용 전·후 두 번이 잠금 보유 시간에 더해진다).

연결: SP17(원본 모사 컨테이너·제한 로그인), SP18(스냅샷 불가 사유), 공용 계약(`KEYSET_HASH`, `OUTSIDE_TABLE_CHANGED`, `allowKeysetVerification`).

## 실패 시 볼 곳

B의 5단계가 `WEAK_VERIFICATION_NOT_ACCEPTED`이면 `allowKeysetVerification`이 안 실린 것이다. `precondition_failed`의 `preconditionFailures`를 본다. 기준선에 `sp21`이 없으면 `sp21` 미리보기 자체가 거부된다(2단계 새로 고침 누락). 방해 세션이 먼저 끝나 버렸으면(90초) 다시 시작한다.

### 확인한 사실 / 추정 / 설계 반영

증거 범위: DB 실측(컨테이너 2대) + Host 개발 모드 API(Split). 동시 [적용] 두 건의 경합, SingleServer 모드의 잠금 대기(원본 LOCK_TIMEOUT은 Split에서만 건다, `OriginDatabase.cs:131`), 큰 DB의 해시 시간(cl20 키우기·SP19)은 범위 밖이다.

확인한 사실:
- `CHECKSUM_AGG(BINARY_CHECKSUM(*))`는 값 +1·대소문자·varchar(max) 변경을 잡고, **같은 열 값을 두 행끼리 맞바꾸면 못 잡는다**(m2). xml 열만 바꾸면 못 잡는다(m5). 순 변경이 없으면 당연히 못 잡는다(m3). 제품의 [적용] `limitations` 문구는 이미 "행끼리 값을 맞바꾸는 변경 … 비교 불가 형식 … 놓칠 수 있음"을 적고 있어 실측과 맞는다(SP17 [적용] 2차 응답). 틀린 것은 SP21 가설 H1이다.
- 원본에만 있는 트리거가 미리보기 밖 테이블을 행 수 그대로 바꾸면 약한 검증이 `OUTSIDE_TABLE_CHANGED`로 잡고 롤백한다(B). 원본은 그대로다.
- 원본 행이 다른 세션에 잠겨 있으면 [적용]은 `LOCK_TIMEOUT`(10초) 뒤 실패하고 원본을 바꾸지 않으며, 잠금이 풀리면 다시 할 수 있다. 무한 대기는 없다.
- **제품 결함(재현됨)**: 잠긴 행이 미리보기에 있던 테이블이면(드리프트 확인이 그 행을 잠금 읽기, `ApplySteps.cs:253` `lockRows: true`) 1222가 `ApplyService.ExecuteAsync`의 드리프트 단계(`ApplyService.cs:290`)에서 잡히지 않아 API 500 "서버 내부 오류입니다"가 된다. 사용자에게 잠금 때문이라는 사실도, 오류 번호도 보이지 않는다. 같은 1222라도 미리보기 밖 테이블이면 8단계(KEYSET 실행 전 상태 읽기, `ApplyService.cs:305-319`)가 잡아 `status = error`와 문구를 낸다.
- 해시 한 번 비용: AW 규모(71테이블 76만 행)에서 따뜻한 캐시 약 0.45초, 차가운 캐시 약 0.94초. KEYSET_HASH는 이것을 [적용] 트랜잭션 안에서 두 번(전·후) 하므로 잠금 보유 시간이 AW 규모에서 약 0.9~1.9초 늘어난다(추정: 2배 계산). CascadeLab 규모는 수 ms.

추정: SingleServer 모드에서는 원본 LOCK_TIMEOUT을 걸지 않아 같은 드리프트 잠금이 명령 시간 제한까지 기다린 뒤 같은 500 경로로 갈 것이다(재지 않음). `SUM(CAST(BINARY_CHECKSUM(...) AS bigint))`를 해시에 더하면 맞바꾸기를 잡을 가능성이 높지만 이번 표본 1건만 봤다.

설계 반영:
- 정정 필요: SP21 H1의 기대(m2 검출) → 실측 미검출. "약한 검증의 한계" 항목에 "같은 열 값을 행끼리 맞바꾸는 변경"을 계속 둔다(이미 제품 문구에 있음).
- 선택 개선(제안): KEYSET 해시 튜플에 `SUM(CAST(BINARY_CHECKSUM(열) AS bigint))`를 더한다(같은 스캔 한 번, 추가 비용 작음). 더하면 맞바꾸기 m2 같은 경우를 잡는지 단위·DB 테스트로 확인한다.
- 제품 수정 제안(C 결함): `ApplyService.ExecuteAsync`의 7단계 `conn.CheckDriftAsync`(`ApplyService.cs:290`)를 8단계와 같은 방식으로 감싼다: `SqlException`(1222, 명령 시간 초과 -2 등, `SandboxUnavailableException`·취소 제외)이면 롤백하고 `ApplyStatus.Error`와 "원본의 미리보기 행이 다른 세션에 잠겨 있어 LOCK_TIMEOUT(10000ms) 뒤 실행하지 않고 롤백함(오류 1222). 잠시 뒤 다시 [적용]할 것"을 돌려준다. 8단계 문구에도 오류 번호를 넣는다(지금은 SqlException 메시지만 있어 "1222"가 없다). 기다린 시간이 `timingsMs.commit`에 들어가는 것도 drift 칸으로 옮긴다. 검증 테스트: `ApplyServiceFlowTests`에 가짜 원본 연결의 `CheckDriftAsync`가 1222 예외를 던질 때 `ApplyAsync`가 예외 없이 `Status = Error`, 메시지에 "1222", 로그에 run·commit 없음(기존 `Keyset_hash_state_read_failure_before_statements_is_error_without_running`과 같은 모양), DB 테스트로 두 세션(한쪽이 미리보기 행 잠금)에서 Split [적용]이 `error`로 끝나고 원본 불변.
