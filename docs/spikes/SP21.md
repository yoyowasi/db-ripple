# SP21 — KEYSET_HASH(약한 검증)의 검출력과 비용

**상태: 준비됨, 미실행(2026-11-13).** 스크립트는 정적 검토만 했다(ScriptDom TSql170 파싱 오류 0). 결과 칸은 비어 있다.

## 목적

원본 스냅샷을 만들 수 없을 때 [적용]은 약한 검증(`verification.mode = KEYSET_HASH`, 동의 필요)을 쓴다: 미리보기에 없던 테이블의 `COUNT_BIG(*)`·`CHECKSUM_AGG(BINARY_CHECKSUM(*))`가 바뀌면 `OUTSIDE_TABLE_CHANGED`로 막고 롤백한다. 이 장치가 실제로 얼마나 잡고 얼마나 놓치는지, 비용은 얼마인지 잰다.
1. **검출력(해시 수준)**: 같은 행 수로 값만 바뀌는 변경, 두 행 값 맞바꾸기, 바꿨다 되돌리기, 대소문자만 바꾸기, xml 열만 바꾸기를 해시가 알아채는가. 알려진 틈(비교 불가 형식)이 어디인가.
2. **검출력(제품 수준)**: 원본에만 있는 트리거가 미리보기 밖 테이블을 행 수 그대로 UPDATE할 때 [적용]이 `OUTSIDE_TABLE_CHANGED`로 막고 롤백하는가.
3. **동시 세션 쓰기**: [적용] 중 다른 세션이 같은 행을 잡고 있으면 어떻게 실패하는가(롤백 쪽 실패, LOCK_TIMEOUT).
4. **트랜잭션 안 시간**: 모든 사용자 테이블의 해시를 한 번 계산하는 데 걸리는 시간(적용 전·후 두 번이 잠금 보유 시간에 더해진다).

연결: SP17(원본 모사 컨테이너·제한 로그인), SP18(스냅샷 불가 사유), 공용 계약(`KEYSET_HASH`, `OUTSIDE_TABLE_CHANGED`, `allowKeysetVerification`).

## 방법과 실행 순서

### A. 해시 검출력(미니 DB, 어느 컨테이너든)

```powershell
.\scripts\run-sql.ps1 spikes\sql\sp21_10_hash_detection.sql -Part 1 -Log spikes\logs\sp21-10-part1.log
.\scripts\run-sql.ps1 spikes\sql\sp21_10_hash_detection.sql -Part 2 -Database SpikeLab_SP21 -ContinueOnError -Log spikes\logs\sp21-10-part2.log
.\scripts\run-sql.ps1 spikes\sql\sp21_99_drop.sql -Log spikes\logs\sp21-99-drop.log   # 정리
```
시나리오 m1~m6 각각을 트랜잭션 안에서 바꾸고 해시 전후를 `dbo.HashResult`에 남긴다(롤백).

### B. 원본에만 있는 트리거(제품 수준, SP17 환경 필요)

사전: SP17 1~7단계(원본 컨테이너, CascadeLab, 제한 로그인, Split Host 기준선). 모든 `sp_container-run.ps1` 호출 앞에 `$env:COMPOSE_PROFILES = 'origin'`.

```powershell
# 1) 원본에 sp21 스키마(X 대상, Y 미리보기 밖, Z 무관) — 트리거는 아직 없다
.\spikes\sql\sp_container-run.ps1 spikes\sql\sp21_21_outside_trigger_setup.sql -Database CascadeLab -Log spikes\logs\sp21-21-setup.log
# 2) Host(Split)에서 기준선을 새로 고친다(샌드박스에도 sp21 스키마가 생기게) → state ready
$h = @{ 'X-DbRipple-Request' = '1' }
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5080/api/sandbox/refresh -Headers $h
do { Start-Sleep 3; $s = Invoke-RestMethod http://127.0.0.1:5080/api/sandbox } until ($s.state -in 'ready','error'); $s.state
# 3) 미리보기: 샌드박스에는 트리거가 없으니 X만 바뀐다
$p = Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5080/api/previews -Headers $h -ContentType 'application/json; charset=utf-8' -Body (@{ sql = 'UPDATE sp21.X SET v = v + 1 WHERE id = 1;' } | ConvertTo-Json)
$p.status; $p.netSummary | ConvertTo-Json -Depth 5
# 4) 원본에 트리거를 추가한다(X UPDATE → Y 한 행 UPDATE, 행 수 그대로)
.\spikes\sql\sp_container-run.ps1 spikes\sql\sp21_22_outside_trigger_add.sql -Database CascadeLab -Log spikes\logs\sp21-22-add.log
# 5) [적용] (약한 검증 동의): OUTSIDE_TABLE_CHANGED로 막고 롤백해야 한다
$a = @{ sqlHash = $p.sqlHash; allowKeysetVerification = $true } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri ("http://127.0.0.1:5080/api/previews/" + $p.previewId + "/apply") -Headers $h -ContentType 'application/json' -Body $a | ConvertTo-Json -Depth 8
# 6) 원본 값 확인: 롤백됐다면 X·Y 모두 v = 0
.\spikes\sql\sp_container-run.ps1 spikes\sql\sp21_24_outside_trigger_check.sql -Database CascadeLab -Log spikes\logs\sp21-24-check.log
```
(Host가 `ready`가 아니면 기준선 새로 고침 오류를 먼저 본다. 6단계의 `apply` 응답에서 `status`, `verification.mode`, `verification.mismatches[].kind`를 적는다.)

### C. 동시 세션 쓰기

B의 3단계(미리보기)까지 한 뒤 **새 창에서** 방해 세션을 켜고(약 90초 동안 X의 id = 1 행을 잠근다) 곧바로 [적용]을 한다.

```powershell
$env:COMPOSE_PROFILES = 'origin'
.\spikes\sql\sp_container-run.ps1 spikes\sql\sp21_30_concurrent_writer.sql -Database CascadeLab -Log spikes\logs\sp21-30-writer.log
# (방해 세션이 도는 동안, 다른 창에서) B의 5단계 [적용] 호출
```
`DbRipple:OriginLockTimeoutMs`(기본 10000ms)가 지나면 [적용]이 실패해야 한다. 응답·Host 로그의 오류 번호(1222 예상)와 화면 문구, 원본에 변경이 없는지(`sp21_24`)를 적는다.

### D. 트랜잭션 안 시간

```powershell
.\scripts\run-sql.ps1 spikes\sql\sp21_40_hash_time.sql -Database AW_Origin -Log spikes\logs\sp21-40-aw.log
.\scripts\run-sql.ps1 spikes\sql\sp21_40_hash_time.sql -Database CascadeLab -Log spikes\logs\sp21-40-cl.log
```
3회씩 재서 첫 회(차가운 캐시)와 뒤 둘을 구분한다. 큰 표본: `scripts\demo\dm6-generate.sql`로 cl20을 키운 뒤 다시 잰다(선택).

## 통과 기준

| 부분 | 기준 |
|---|---|
| A | 판정 H1(m1·m2·m4·m6 검출), H2(m3 순 변경 없음은 미검출), H3(m5 xml 열은 미검출 = 알려진 틈 확인)이 PASS이거나, FAIL이면 실측값으로 `limitations` 문구를 정정한다. **틈(미검출)은 [적용] 화면에 "약한 검증의 한계"로 적을 항목이다** |
| B | 약한 검증 [적용]이 `OUTSIDE_TABLE_CHANGED`(대상 테이블 `sp21.Y`)로 막히고 원본의 X·Y가 그대로다. 막지 못하고 커밋되면 FAIL(검출력 부족 → 약한 검증의 한계 문구를 강화) |
| C | 방해 세션이 있을 때 [적용]이 데이터 손상 없이 실패하고(원본 변경 없음) 오류 번호·문구가 사용자에게 의미 있게 보인다. 못 잡고 무한 대기하면 FAIL |
| D | AW·CascadeLab에서 해시 한 번(전체 테이블) 시간 p50을 기록한다. **잠금 보유 시간 허용선은 사용자가 정한다**(판단 기준 5: 초과 시 약한 검증 제안 조건 표기) |

## 실패 시 볼 곳

B의 5단계가 `WEAK_VERIFICATION_NOT_ACCEPTED`이면 `allowKeysetVerification`이 안 실린 것이다. `precondition_failed`의 `preconditionFailures`를 본다. 기준선에 `sp21`이 없으면 `sp21` 미리보기 자체가 거부된다(2단계 새로 고침 누락). 방해 세션이 먼저 끝나 버렸으면(90초) 다시 시작한다.
