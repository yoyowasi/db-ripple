# SP19 — 큰 DB 시간: Split 기준선·다음 미리보기 준비·KEYSET_HASH 해시

**상태: 2026-11-16 Codex 클라우드 cl·0g3·1g·AW 각 3회 실측 완료 + 로컬 큰 DB 부분 측정.** 클라우드 Q1 12/12 ready·지문 일치·불일치 0, 미리보기 18/18 ready, 허용된 실제 apply 9/9 committed. 합성 1g의 apply 잠금 보유 중앙값은 4.862초로 이번 환경에서는 10초에 도달하지 않았다. 원본도 SQL 2025이므로 **16→17 업그레이드 복원 없음**. 제품 결함은 찾지 못했고 실행기 두 곳만 최소 수정했다. 2g/5g는 클라우드에서 실행하지 않았으며 5GB 판정은 추정이다. 이전 로컬 결과와 클라우드 결과는 아래에서 분리한다. 상세 회차·환경·초기 실패·검증·정리는 [클라우드 보고서](../test-reports/2026-11-16-sp19-cloud.md)를 본다.

## 목적

SP17은 Split 기준선이 6~9초라고 적었지만 DB가 작았다(백업 약 0.6MB, SP17.md 194행). SP21은 큰 DB의 해시 시간을 범위 밖으로 뒀다(SP21.md 124행). 이 스파이크는 DB가 커질 때 아래 세 시간이 어떻게 늘어나는지, 제품의 시간 제한에 걸리는지 잰다.

- **Q1. Split 기준선 단계별 시간**: 원본 COPY_ONLY 백업 → 가져오기 폴더 복사 → 샌드박스 복원 → 소유자 정리 → 감사 트리거 설치 → 스냅샷.
- **Q2. 미리보기 한 번 뒤 다음 미리보기 준비 시간**: 제품 경로(미리보기 뒤 샌드박스 상태)와 스냅샷 되돌리기 시간.
- **Q3. KEYSET_HASH 해시 시간**: 원본 전체 테이블 해시가 큰 DB에서 몇 초인지, 원본 LOCK_TIMEOUT·명령 시간 제한에 걸릴 수 있는지.

연결: SP17(원본 모사 컨테이너·제한 로그인·Split Host), SP21(해시 측정 `sp21_40_hash_time.sql`), SP5(스냅샷 되돌리기 411ms, AW), architecture.md A13·A14·D2.

**Q2의 전제.** 제품은 미리보기마다 샌드박스를 스냅샷으로 되돌리지 않는다. 미리보기는 트랜잭션 안에서 실행하고 ROLLBACK한다(D2, `PreviewExecutor.cs:15-16`·`:284`). 롤백 뒤에도 확정된 감사 기록이 남으면 dirty로 표시하고 사용자가 새로 고침(=Q1 전체 재구축)을 한다. 스냅샷 되돌리기는 평가 회차 초기화에만 쓴다(architecture.md 133·1036행). 그래서 Q2는 (1) 미리보기 직후 상태가 `ready`인지(다음 미리보기에 준비 단계가 따로 없는지), (2) 미리보기 시간이 크기에 따라 어떻게 느는지, (3) 되돌리기 시간(평가 초기화, dirty 때 재구축 대신 쓸 후보)을 잰다.

## 측정 방법

**단계별 시간을 어디서 읽나.** Host는 기준선 단계별 시간을 로그나 상태 API에 내지 않는다(`SandboxManager.BuildAsync`가 `SqlBaselineSteps`·`SqlOriginSteps`를 `log` 없이 만든다, SandboxManager.cs:225-227. 상태 API에는 `baselineAt`만 있다). 그래서 제품 코드는 그대로 두고 **두 서버의 확장 이벤트 세션 `sp19_trace`**(응용 프로그램 이름 `db-ripple` 연결의 `sql_batch_completed`·`rpc_completed`)로 Host가 보낸 명령마다 서버 시간을 남긴다. 두 컨테이너는 같은 Docker 호스트 커널 시계를 쓴다. 복사 단계는 Host 안의 파일 복사라 서버 명령이 없으므로 "원본 BACKUP 끝 → 샌드박스 다음 명령 시작" 간격으로 잰다(그 사이에 Host가 하는 일은 복사뿐이다, BaselineBuilder.cs:99-108). 전체 시간은 클라이언트에서 POST → `ready`(250ms 간격 폴링)로 잰다. 단계 정의는 `sp19_30_measure.ps1` 머리말에 있다.

## Codex 클라우드에서 돌리기

환경 가정: Linux, PowerShell 7(`pwsh`), Docker, .NET SDK 10, 루트 디스크 약 8GB(2026-11-15 클라우드는 SQL 이미지 vfs 복제로 ENOSPC가 났고, 경량 이미지 `dbripple-sql-thin:cloud` + 메모리 디스크의 `/opt/mssql` 읽기 전용 바인드로 SQL Server 2025 CU10을 띄웠다. docs/test-reports/2026-11-15-cloud-db-validation.md). 아래 명령은 저장소 루트에서 한다. **2026-11-16 새 Linux 클라우드에서 실제 실행했다.** 새 환경에는 SDK·PowerShell·SQL 컨테이너가 없었고, 공식 MCR 레이어로 경량 SQL 환경 두 대를 새로 준비했다. 환경 준비·실패 원인·실측은 [클라우드 보고서](../test-reports/2026-11-16-sp19-cloud.md)를 본다.

### 1. `.env`

`.env`에 다음 값이 있어야 한다(비밀번호는 직접 입력, `$` 없이 8자 이상·3종 이상. 값은 출력하지 않는다):

```
MSSQL_SA_PASSWORD=<…>
ORIGIN_SQL_SERVER=127.0.0.1,14334
ORIGIN_SQL_USER=dbr_origin_user
ORIGIN_SQL_PASSWORD=<…>
ORIGIN_SQL_TRUST_CERT=true
```

### 2. 폴더·권한·여유 확인

```bash
mkdir -p .data/origin-backup .data/import .data/backup
chmod 777 .data/origin-backup .data/import        # 컨테이너 mssql 사용자(uid 10001)가 .bak을 쓰고(원본) 읽는다(샌드박스)
umask 022                                      # Host가 만든 가져오기 사본·사전 점검 파일을 SQL이 읽어야 한다
df -h . "$(docker info -f '{{.DockerRootDir}}')"; free -m; docker system df
```
원본 SQL이 쓴 .bak을 Host가 읽어 복사할 수 있어야 한다. 이번 rootless 환경에서는 SQL 파일 소유자가 Host에서 nobody로 보였고, SQL이 백업 권한을 0660으로 정해 `setfacl -d -m o::r`만으로는 부족했다. `setfacl -d -m "u:$(id -u):r--" .data/origin-backup`으로 Host UID 읽기 ACL을 주고, 실제 COPY_ONLY 백업을 Host가 열 수 있는지 확인했다. 사전 확인의 `echo` 쓰기·읽기 probe만으로 SQL 백업 권한까지 검증했다고 판단하지 않는다. rootless DockerRootDir에 접근할 수 없으면 스크립트는 샌드박스 `/var/opt/mssql` 볼륨의 `df`로 기존 공간 기준을 적용하며, 조회 실패는 거부한다. `/proc/meminfo` 외에 cgroup 메모리 한도·현재 사용량·OOM 기록도 직접 확인한다.

### 3. 컨테이너 두 대

샌드박스 `dbripple-sql`(127.0.0.1:14333, `/var/opt/mssql/import` ← 저장소 `.data/import`)와 원본 모사 `dbripple-sql-origin`(127.0.0.1:14334, `/var/opt/mssql/backup` ← 저장소 `.data/origin-backup`)이 떠 있어야 한다. 이름이 다르면 `-SandboxContainer`·`-OriginContainer`로 넘긴다. 두 서버의 `@@SERVERNAME`은 달라야 한다(같으면 제품이 기준선을 거부한다).

A. 디스크가 넉넉할 때(compose):

```bash
docker compose up -d sql                                                   # 샌드박스(2025 CU10), 없을 때만
ORIGIN_IMAGE_TAG=2025-CU10-ubuntu-24.04 docker compose --profile origin up -d sql-origin   # 원본을 같은 이미지로(이미지 하나만 받음)
# 로컬과 같은 2022 원본이 필요하면 ORIGIN_IMAGE_TAG 없이(2022-latest 이미지를 하나 더 받는다. 디스크 여유가 있을 때만)
```

B. 2026-11-15 클라우드처럼 샌드박스가 경량 이미지 + `/opt/mssql` 바인드로 떠 있을 때(같은 이미지·바이너리를 원본에도 쓴다. **확인하지 않은 명령**):

```bash
IMG=$(docker inspect -f '{{.Config.Image}}' dbripple-sql)
BIN=$(docker inspect -f '{{range .Mounts}}{{if eq .Destination "/opt/mssql"}}{{.Source}}{{end}}{{end}}' dbripple-sql)
docker inspect -f '{{range .Mounts}}{{.Destination}} <- {{.Source}}{{"\n"}}{{end}}' dbripple-sql   # /var/opt/mssql/import <- <저장소>/.data/import 가 있어야 한다
set -a; . ./.env; set +a                                                   # MSSQL_SA_PASSWORD를 셸 환경으로(출력하지 않는다)
docker run -d --name dbripple-sql-origin -h sp19-origin -p 127.0.0.1:14334:1433 --memory 3g \
  -e ACCEPT_EULA=Y -e MSSQL_PID=Developer -e MSSQL_SA_PASSWORD -e MSSQL_AGENT_ENABLED=false \
  -e MSSQL_MEMORY_LIMIT_MB=2048 -e MSSQL_COLLATION=SQL_Latin1_General_CP1_CI_AS \
  -v dbripple-sp19-origin-data:/var/opt/mssql -v "$PWD/.data/origin-backup:/var/opt/mssql/backup" \
  ${BIN:+-v "$BIN:/opt/mssql:ro"} "$IMG"
```
샌드박스에 `.data/import` 바인드가 없으면 compose 설정(`./.data/import:/var/opt/mssql/import`)대로 다시 만들어야 한다. 그건 이 스파이크 밖의 환경 작업이므로 멈추고 알린다.

- 측정 스크립트 결함: SQL Server 2022 CU28에서 `sys.fn_xe_file_target_read_file(...)`의 `timestamp_utc`를 매개변수와 직접 비교하면 0행이 나온다(2025 CU10은 정상, 같은 파일에서 30행 확인). `DATEADD(millisecond, 0, timestamp_utc)`로 감싸면 된다. 이 때문에 CL 1~3회차는 원본 쪽 단계가 비었고, 고친 뒤 4~6회차로 다시 쟀다.
- CL `cl07a` 미리보기는 문장 실패(2627, `PK_cl07_C` 중복 11): SP17 [적용]이 원본 CascadeLab의 cl07.C에 10·11행을 넣었고 기준선이 그 상태를 복원했기 때문이다. 크기와 무관하다. 순 변경 없는 `cl02dept`로 바꿨다(그래서 CL의 netDiff가 1~2ms다). 처음 고른 `sp21.Z`는 sp21 스키마가 원본에서 지워져 HTTP 422였다(CSV 행 없음).
- 리눅스 컨테이너에서 스냅샷 스파스 파일 크기(`sys.dm_io_virtual_file_stats.size_on_disk_bytes`)가 0으로만 나와 바꾼 페이지 양을 재지 못했다(스크립트에서 그 열을 뺐다).
- 되돌리기 뒤 샌드박스 로그 파일이 1MB 미만으로 다시 만들어진다(문서화된 동작). 그 뒤 큰 미리보기는 로그 자동 증가를 탄다.
- `ALTER DATABASE … SET SINGLE_USER WITH ROLLBACK IMMEDIATE`가 회차 3번 중 1~2번 약 3초 걸렸다("Nonqualified transactions are being rolled back"). Host는 꺼져 있었다. 원인은 확인하지 못했다(되돌리기 시간에는 넣지 않았다).
- 2026-11-16 로컬 스크립트는 Windows 전용이었다(`Get-CimInstance`, `\` 경로, `docker compose` 서비스 이름, 전경 Host). 클라우드용으로 바꾼 점은 아래 "Linux 호환"에 있다.

**Linux 호환(2026-11-16 수정, 이후 새 클라우드에서 실제 검증)**: 경로는 `Join-Path`와 `/`만 쓴다. ### 로컬 부분 측정 당시의 사실 / 추정 / 설계 반영

확인한 사실(로컬, 0.3GB까지와 2GB 1회):
- Split 기준선은 0.3GB 약 5.8초, 2GB 약 26.9초(1회)이고 시간 초과 없이 끝난다. 2GB에서 원본 BACKUP(압축)이 절반을 차지한다. 감사 설치는 크기가 아니라 테이블 수에 비례한다.
- 미리보기 뒤 샌드박스는 계속 `ready`다(다음 미리보기 준비 단계 없음). 문장이 실패한 미리보기도 마찬가지다.
- 같은 1행 UPDATE의 미리보기 시간은 바뀐 테이블 크기에 비례한다(최종 차이가 테이블 전체를 스냅샷과 조인).
- 스냅샷 되돌리기(0.35~0.83초)는 같은 크기의 RESTORE 명령(0.95~1.44초)보다 짧다.
- KEYSET_HASH는 0.3GB에서 해시 한 번 약 0.7~1.2초, [적용] 잠금 보유 약 0.8~2.0초로 커밋됐다. LOCK_TIMEOUT 10초는 해시 스캔 자체로는 걸리지 않았다(잠금 대기가 없었다).
- Host는 기준선 단계별 시간을 남기지 않는다. 이번에는 서버 XE로만 잴 수 있었다.

추정(실측 아님): 5GB 기준선 약 1분, 명령 하나는 최대 약 34초(BACKUP) → Q1-2 PASS 예상. 해시 한 번 5GB 약 22초 → Q3-1 PASS 예상. [적용] 잠금 보유는 약 1GB에서 10초(다른 db-ripple [적용]의 LOCK_TIMEOUT), 약 3GB에서 30초(일반 클라이언트 기본 명령 시간 제한)에 닿는다 → Q3-3은 큰 DB에서 FAIL 예상. 미리보기는 1,000만 행대 테이블을 바꾸면 수십 초.

가설과 다른 값: 없음(정정할 기존 문서 수치 없음). SP17의 "6~9초"는 CascadeLab에서 이번에도 5.3~11.9초로 같은 범위다.

설계 반영(제안, 제품 코드는 고치지 않았다):
- Host 로그에 기준선 단계별 시간을 남긴다: `SandboxManager.BuildAsync`(SandboxManager.cs:225-226)에서 `SqlBaselineSteps`·`SqlOriginSteps`에 `log`(ILogger)를 넘기면 이미 있는 "[db] Nms 첫 줄" 기록이 나온다. 검증: 단위 테스트에서 가짜 로그 수집기로 BACKUP·RESTORE·스냅샷 줄이 남는지, Host 로그에 연결 문자열이 없는지.
- 기준선 명령 시간 제한(600초 고정)을 설정으로 열지는 큰 DB 실측(5GB 이상) 뒤에 정한다(이 PC 처리량이면 약 80GB부터 문제, 추정).
- KEYSET_HASH 동의 화면에 "원본 사용 데이터 약 1GB 이상이면 [적용] 동안 원본 행 잠금이 10초를 넘을 수 있음"을 넣을지는 추가 큰 DB 실측 뒤 정한다(이번 클라우드 1g는 4.862초로 10초 미만이므로 고정 1GB 기준은 채택하지 않는다).
