# SP22 PostgreSQL 18 감사 수집 실측

2026-11-18(KST), Docker `postgres:18`의 PostgreSQL 18.7에서 [SP22 스크립트](../../spikes/sql/sp22_10_pg_capture.sql)를 실행했다. 문장 단위 AFTER 트리거의 전이 테이블이 FK 연쇄와 사용자 트리거의 변경을 어떻게 묶는지 확인했다.

```bash
docker pull postgres:18
docker exec -i dbripple-pg-sp22 psql -X -U postgres -d sp22 -v ON_ERROR_STOP=1 -f - \
  < spikes/sql/sp22_10_pg_capture.sql
```

## 가설별 결과

| 가설 | 실측 |
|---|---|
| H1 전이 테이블이 FK 연쇄를 잡는가 | A·E에서 `child` DELETE, `note` UPDATE(SET NULL), `grandchild` DELETE를 모두 잡았다. E의 부모 삭제는 2행이었고 자식 테이블별 감사 묶음은 각각 하나였다. |
| H2 깊이 | A·E에서 직접 DELETE와 FK 자식·손자·SET NULL이 모두 `pg_trigger_depth() = 1`이었다. D의 사용자 트리거 쓰기는 깊이 2·3이었다. 보강 시험에서 사용자 트리거가 부모를 지운 경우 해당 부모와 FK 묶음이 모두 깊이 2였다. |
| H3 감사 순번 | FK 묶음은 A·E에서 부모부터 기록됐다(전위). D에서는 사용자 트리거가 쓴 묶음부터 기록됐다(후위). |
| H4 0행 문장 | B에서 자식이 없는 부모를 지우자 `child`·`note`가 0행으로 발동했다(깊이 1). C에서 직접 DELETE는 0행으로 발동했고 FK 묶음은 없었다. 보강 시험에서는 깊이 2의 0행 FK 묶음도 확인했다. |
| H5 여러 사건 + 전이 테이블 | 한 트리거에 INSERT·UPDATE·DELETE를 지정하면 SQLSTATE `0A000`이었다. 사건별 트리거 3개를 설치했다. |
| H6 RI 카탈로그 | `s.parent`·`s.child`의 내부 RI 트리거 8개는 모두 `tgisinternal = true`와 `tgconstraint <> 0`이었다. `pg_constraint`에서 CASCADE는 `confdeltype = 'c'`, SET NULL은 `'n'`이었다. |
| H7 롤백 | A에서 롤백 전에 감사 4개를 읽었고 롤백 후 0개였다. 다음 시나리오의 순번은 계속 증가했다. |

## 시나리오 A~E

아래 열의 순서는 감사 순번이다. 괄호 안은 `깊이, 이전 행 수 → 이후 행 수`이며 테이블 스키마는 모두 `s`다.

| 시나리오 | 직접 문장의 영향 행 | 감사 기록 |
|---|---:|---|
| A. `DELETE parent WHERE id = 1` | 1 | 1 parent DELETE (1, 1→0) → 2 child DELETE (1, 2→0) → 3 note UPDATE (1, 2→2) → 4 grandchild DELETE (1, 3→0) |
| B. `DELETE parent WHERE id = 3` | 1 | 5 parent DELETE (1, 1→0) → 6 child DELETE (1, 0→0) → 7 note UPDATE (1, 0→0) |
| C. `DELETE parent WHERE id = 99` | 0 | 8 parent DELETE (1, 0→0) |
| D. `UPDATE order_lines SET qty = qty + 1 WHERE id = 70` | 1 | 9 history INSERT (3, 0→1) → 10 orders UPDATE (3, 1→1) → 11 orders UPDATE (2, 1→1) → 12 order_lines UPDATE (1, 1→1) |
| E. `DELETE parent WHERE id IN (1,2)` | 2 | 13 parent DELETE (1, 2→0) → 14 child DELETE (1, 3→0) → 15 note UPDATE (1, 3→3) → 16 grandchild DELETE (1, 3→0) |

### RI 문장과 감사 묶음

E를 새 psql 세션에서 한 번 더 실행하며 내부 문장 실행을 기록했다.

```sql
LOAD 'auto_explain';
SET auto_explain.log_min_duration = 0;
SET auto_explain.log_nested_statements = on;
SET auto_explain.log_analyze = on;
SET client_min_messages = log;
BEGIN;
DELETE FROM s.parent WHERE id IN (1,2);
ROLLBACK;
```

내부 RI 문장은 부모 행별로 나뉘었다. `child` DELETE와 `note` UPDATE는 `parent_id` 1·2에 대해 각각 두 번, `grandchild` DELETE는 `child_id` 10·11·20에 대해 세 번 실행됐다. E의 전이 테이블 감사에는 테이블별로 합쳐진 묶음 하나씩이 기록됐다.

### 사용자 트리거 안의 FK와 0행 묶음

SP22 비즈니스 스키마를 복제한 별도 원본 `sp22_nested`에 아래 트리거를 추가하고, Host에서 새로 고침한 샌드박스와 미리보기로 확인했다.

```sql
CREATE FUNCTION s.nested_delete() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  DELETE FROM s.parent WHERE id = 2;
  RETURN NULL;
END $$;
CREATE TRIGGER t_sp22_nested AFTER DELETE ON s.parent FOR EACH ROW
  WHEN (OLD.id = 3) EXECUTE FUNCTION s.nested_delete();
```

`DELETE FROM s.parent WHERE id = 3`에서 안쪽 parent DELETE, child DELETE, note UPDATE, 0행 grandchild DELETE가 모두 깊이 2였다. 이 묶음들 뒤에 바깥 parent DELETE와 0행 child DELETE·note UPDATE가 깊이 1로 기록됐다. 기존 보정은 안쪽 child·note를 깊이 1로 낮춰 안쪽 parent의 트리거 귀속을 깨뜨렸고, 기존 0행 규칙은 안쪽 grandchild 헤더를 누락했다.

### TEMPLATE 복제

psql 세션 하나를 `sp22`에 유지한 채, 다른 세션에서 관리 DB `postgres`에 연결해 실행했다.

```sql
\set VERBOSITY verbose
CREATE DATABASE sp22_templatecheck TEMPLATE sp22;
```

연결이 열려 있을 때 `55006`과 `There is 1 other session using the database.`가 반환됐다. 원본 세션의 `pg_backend_pid()`는 실패 전후 동일했고 같은 세션에서 쿼리가 계속 실행됐다. 원본 psql을 정상 종료한 뒤 동일한 CREATE가 성공했다. 검증용 복제 DB는 삭제했다.

## 설계 반영과 범위

감사 헤더의 순번과 깊이를 그대로 전달하고, 변경 행이 없는 묶음도 헤더를 보존한다. 결과는 SP22 테이블·트리거와 PostgreSQL 18.7에서의 관측이며, 다른 버전이나 모든 스키마에서 같은 순서를 보장한다는 근거는 없다. Host에서 원인과 순 변경을 검증한 결과는 별도 보고서에 있다. [설계 결정 2·5](../superpowers/specs/2026-11-18-postgres-preview-minimal.md) · [클라우드 검증](../test-reports/2026-11-18-pg-minimal-cloud.md)
