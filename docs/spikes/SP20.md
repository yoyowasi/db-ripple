# SP20 — 고아 dbo와 EXECUTE AS OWNER

**상태: 실행 완료(2026-11-16). 통과(세 가지 모두 분명해짐), 판정 H1 PASS.** 복원 직후 `sys.databases`의 소유자는 **sa**(복원한 로그인)였지만 DB 안 `dbo` 사용자는 원본 소유자 SID 그대로라 **고아**였고, EXECUTE AS OWNER 프로시저가 **15517**로 실패했다. `ALTER AUTHORIZATION … TO sa` 뒤에는 `dbo`가 sa로 다시 묶여 프로시저·트리거가 오류 없이 돈다. 기준 1의 판단 문구("sa이면 안전장치")는 정정이 필요하다(아래). 로그 `spikes/logs/sp20-*.log`, `logs/home-test/2026-11-16/sp20/`. 스크립트는 고치지 않았다. 2026-11-13 준비 때는 정적 검토만 했다(ScriptDom TSql170 파싱 오류 0).

## 목적

Split에서는 다른 로그인이 소유한 원본 DB의 백업을 로컬 샌드박스에서 sa로 복원한다. 원본의 소유자 로그인은 로컬에 없다(Windows 로그인이면 SID도 없다).
- 복원 뒤 DB 소유자와 `dbo` 사용자는 무엇이 되는가(원본 SID 유지 = 고아 / 복원한 로그인으로 바뀜).
- `WITH EXECUTE AS OWNER`로 만든 프로시저·트리거가 복원 직후 실행되는가, 고아 dbo면 어떤 오류(15517 등)가 나는가.
- 제품의 복원 뒤 정리(`BaselineSql.AfterRestoreLocal`: `ALTER AUTHORIZATION ON DATABASE::… TO sa`) 전후로 결과가 어떻게 달라지는가.

연결: SP10(실행 주체, 소유권 체인), SP17(Split), `BuildSplitAsync`의 소유자 정리 단계.

## 방법

1. 원본 모사 컨테이너(2022)에서 SQL 로그인 `sp20_owner`(비밀번호는 NEWID로 즉석 생성, 출력 안 함)를 만들고 `SpikeLab_SP20`의 소유자로 한다. `WITH EXECUTE AS OWNER` 프로시저 `usp_as_owner`와 트리거 `trg_T_upd`가 `ORIGINAL_LOGIN()`·`SUSER_SNAME()`·`USER_NAME()`을 `dbo.Whoami`에 남긴다(`sp20_10_origin_prep.sql`).
2. 원본에서 COPY_ONLY 백업(`sp20_20_origin_backup.sql`) → 호스트에서 가져오기 폴더로 복사.
3. 샌드박스(2025) sa로 복원(`sp20_30_sandbox_restore_check.sql`): 소유자·`dbo` 매핑·`usp_as_owner`·트리거 실행(롤백 안) 확인.
4. `ALTER AUTHORIZATION … TO sa` 뒤 같은 확인(`sp20_40_alter_authorization_check.sql`).

## 결과 (2026-11-16 실측)

환경: 원본 모사 Microsoft SQL Server 2022 (RTM-CU28) (KB5125472) 16.0.4325.4 (X64) Developer, 샌드박스 Microsoft SQL Server 2025 (RTM-CU10) (KB5125471) 17.0.5035.5 (X64) Enterprise Developer, 둘 다 Linux 컨테이너. 백업 `sp20_owner_db.bak` 3,985,408B(COPY_ONLY, 압축 없음). 샌드박스에는 `sp20_owner` 로그인이 없었다(경고 줄 없음). 복원은 2022 → 2025 업그레이드(DB 버전 957 → 998, 단계 메시지 40줄)로 0.037초. 논리 이름은 가정대로 `SpikeLab_SP20`·`SpikeLab_SP20_log`.

| 시점 | db_owner | dbo가 매핑한 로그인 | usp_as_owner 오류 | Whoami(suser) |
|---|---|---|---|---|
| 원본 | sp20_owner | sp20_owner | 없음 | proc·trigger 2행, origLogin sa, suser **sp20_owner**, usr dbo |
| 샌드박스 복원 직후(전) | **sa**(owner_sid 0x01 = sa SID) | **(null: orphan)** | **15517** "Cannot execute as the database principal because the principal "dbo" does not exist, this type of principal cannot be impersonated, or you do not have permission." | 행 없음(실행 안 됨) |
| ALTER AUTHORIZATION 후 | sa | sa | 없음 | proc·trigger 2행, origLogin sa, suser **sa**, usr dbo |

판정 표: H1(조치 뒤 모듈이 오류 없이 실행) **PASS**(errNo=none rows=2). 로그 `sp20-10-prep.log`, `sp20-30-restore.log`, `sp20-40-after.log`. 정리: 양쪽 `sp20_99_drop.sql`(DB·로그인 삭제), 호스트 `.bak` 두 개 삭제.

통과 기준별:
1. `before_fix_db_owner` = **sa**(NULL 아님). 그러나 같은 시점 `dbo`는 고아다. 기준 1의 판단("sa이면 제품의 소유자 정리는 안전장치, NULL이면 필수")은 **정정 필요**: `sys.databases.owner_sid`는 복원한 로그인(sa)으로 바뀌지만 DB 안 `dbo`의 SID는 원본 소유자 그대로라, 소유자가 sa로 보여도 소유자 정리(ALTER AUTHORIZATION)는 **필수 단계**다.
2. 조치 뒤 모듈 오류 없음, Whoami 2행, suser sa → PASS. 같은 소유자(sa)로 다시 지정해도 `ALTER AUTHORIZATION`이 `dbo` SID를 다시 맞춘다.
3. 조치 전 오류 번호 = **15517**.

### 확인한 사실 / 추정 / 설계 반영

증거 범위: DB 실측(컨테이너 2대, SQL 로그인 소유 DB). Windows 로그인이 소유한 DB·그룹 SID, 원본에서 다른 사용자가 `EXECUTE AS USER = '…'`로 만든 모듈, 원본 사용자 고아(로그인 없는 일반 사용자)는 검증하지 못한 범위다.

확인한 사실:
- 다른 SQL 로그인이 소유한 DB를 다른 서버에 sa로 복원하면 `sys.databases` 소유자는 sa가 되고 `dbo`는 원본 SID를 가진 고아가 된다(두 값이 어긋난다). 이 상태에서 `WITH EXECUTE AS OWNER` 프로시저는 15517로 실패한다. 트리거는 프로시저가 먼저 실패해 발동하지 않아 따로 재지 못했다(같은 이유로 실패할 것으로 추정).
- `ALTER AUTHORIZATION ON DATABASE::… TO sa`(제품 `BaselineSql.AfterRestoreLocal`, `BaselineSql.cs:248-255`, 조건 없이 항상 실행)로 `dbo`가 sa에 묶이고 EXECUTE AS OWNER 프로시저·트리거가 sa로 돈다(SUSER_SNAME = sa).
- 그래서 제품의 Split 기준선이 소유자 검사 없이 ALTER AUTHORIZATION을 항상 하는 지금 방식이 맞다. "owner가 이미 sa면 건너뛰기" 같은 최적화를 넣으면 15517이 다시 난다.

추정: 미리보기에서 15517이 나면 원인은 도구 결함이 아니라 샌드박스 DB의 `dbo` 고아다. 안내 문구 후보: "샌드박스 DB의 dbo가 로컬 로그인과 연결되지 않아 EXECUTE AS OWNER 모듈을 실행할 수 없음(기준선을 새로 고칠 것)". 제품 기준선이 항상 정리하므로 정상 경로에서는 나지 않을 것이다.
가설과 다른 값: 기준 1의 판단 문구(위). 정정 필요.
설계 반영: 실행 주체 비교 시 원본에서는 `SUSER_SNAME()`이 원본 소유자 로그인(이번 sp20_owner), 샌드박스에서는 sa로 다르다. SP17 [적용] 결과의 한계 문구("트리거의 USER_NAME·SUSER_SNAME 값이 다를 수 있음")가 EXECUTE AS OWNER 모듈에도 해당한다.
