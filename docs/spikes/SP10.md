# SP10 — 실행 주체(EXECUTE AS USER)와 감사 트리거 권한

- **목적:** 열린 트랜잭션 안에서 EXECUTE AS USER/REVERT를 반복할 수 있는지, DML 권한만 가진 사용자 문맥에서 감사 트리거의 헤더 INSERT와 NEXT VALUE FOR가 소유권 체인으로 성공하는지 본다(A18).
- **결과:** **성립** — 2026-11-10 실행. 미니 판 판정 6개가 모두 PASS다. AW 판에서도 DML 전용 사용자의 결과(영향 행, 오류, 바뀐 테이블·값, 감사 기록)가 dbo와 같다. 새로 확인한 제약이 하나 있다. 가장 중 트랜잭션이 doomed(XACT_STATE −1)가 되면 REVERT가 3930으로 실패하고, ROLLBACK한 뒤에야 풀린다.
- **증거 범위:** DB 실측(컨테이너 dbripple-sql, SQL Server 2025 RTM-CU10 17.0.5035.5, 2026-11-10). SpikeLab_SP10·SpikeLab_SP10_Other는 끝에서 삭제했다. AW_SpikeB(이 스파이크 전용 AW 복사본)는 실행마다 ROLLBACK했고, 감사 객체·사용자는 끝에서 지웠다.

## 방법

1. 미니 판 `spikes/sql/sp10_10_run.sql`: 1부(master: 두 DB 생성) → `common_audit_store.sql`, `common_hand_audit.sql`(-d SpikeLab_SP10) → `-- PART 2` 이후(끝에서 두 DB 삭제).
   - `spk_user`(WITHOUT LOGIN)는 `dbo` 스키마 DML 권한만 가진다. audit 스키마·SEQUENCE 권한은 없다.
   - 한 트랜잭션 안에서 5회: 가장 → `UPDATE dbo.T`(감사 트리거 발동) → audit 직접 읽기(실패 예상) → REVERT → 다른 DB 읽기. 마지막에 가장한 채 다른 DB 읽기.
   - 음성 대조: `dbo.T2`의 트리거가 `spk_owner` 소유 스키마 `auditx`의 SEQUENCE·테이블에 쓴다.
2. AW 판 `spikes/sql/sp10_20_aw.sql`(2026-11-10 추가): `-Part 1` → `common_audit_store.sql`(-Database AW_SpikeB) → `-Part 2`.
   - 문장: `UPDATE Sales.SalesOrderDetail SET OrderQty = OrderQty + 1` 1행(SalesOrderID 43659, SalesOrderDetailID 1). 이 문장은 iduSalesOrderDetail을 발동한다. iduSalesOrderDetail은 Production.TransactionHistory INSERT, Person.Person 형식화 xml `.modify` 2회(→ iuPerson), SalesOrderHeader UPDATE를 한다. SalesOrderHeader UPDATE는 다시 uSalesOrderHeader를 발동한다(RevisionNumber, `dbo.ufnGetAccounting*()`, SalesPerson·SalesTerritory).
   - `spk_dml`(WITHOUT LOGIN)에는 `SCHEMA::Sales`의 SELECT·INSERT·UPDATE·DELETE만 줬다. 직접 권한 확인 결과: TransactionHistory INSERT, Person UPDATE, IndividualSurveySchemaCollection EXECUTE, dbo 함수·uspLogError EXECUTE, audit 객체 권한이 모두 0이다.
   - 실행 4회(각각 BEGIN TRAN … ROLLBACK): R1 dbo, R2 spk_dml(감사 없음) → 감사 설치 → R3 dbo, R4 spk_dml. 사용자 문장은 모듈 밖 ad hoc 배치에서 실행했다(모듈 안이면 소유권 체인이 섞인다).
   - 실행마다 도구 계정(dbo)으로 REVERT한 뒤 다음을 쟀다: 대상·연쇄 행 값, dbo.ErrorLog 행 수, 전 테이블 지문(행 수/`BINARY_CHECKSUM`/xml 해시), 감사 요약(테이블·연산별 발동 수, 행 수, nestLevel, 발동 순서, 이미지 수).
   - 비교 규칙: 값은 정확히 같아야 SAME이다. Production.TransactionHistory만 IDENTITY·`GETDATE()` 열 때문에 실행마다 지문이 달라지므로 '변경 여부와 행 수'로 비교했다.
   - 감사: 계약 저장소(`common_audit_store.sql`)에 생성기(C9 TriggerSql·SelectItems) 본문 모양의 손 감사 트리거를 더했다. 관련 테이블 6개의 I/U/D 18개를 Last로 설치했다. `common_hand_audit.sql`의 `spike_InstallAudit`는 미니 테이블 모양(Id, Ref, Ref2, Src)을 전제로 해서 AW에 쓸 수 없다. 그래서 같은 본문을 `sys.columns`로 만드는 설치 배치를 sp10_20에 두었다. AW 사용자 트리거의 본문·순서는 바꾸지 않았다.
3. 실행(PowerShell, 저장소 루트). `-ContinueOnError`는 쓰지 않았다(의도한 오류는 TRY/CATCH로 받음). 최종 로그는 모두 첫 줄이 `exit=0`이다.
   ```

   .\scripts\run-sql.ps1 spikes\sql\common_audit_store.sql -Database SpikeLab_SP10 -Log spikes\logs\sp10-10-common-audit-store.log
   .\scripts\run-sql.ps1 spikes\sql\common_hand_audit.sql -Database SpikeLab_SP10 -Log spikes\logs\sp10-10-common-hand-audit.log
   .\scripts\run-sql.ps1 spikes\sql\sp10_10_run.sql -Part 2 -Database SpikeLab_SP10 -Log spikes\logs\sp10-10-part2.log
   .\scripts\run-sql.ps1 spikes\sql\sp10_20_aw.sql -Part 1 -Database AW_SpikeB -Log spikes\logs\sp10-20-aw-part1.log
   .\scripts\run-sql.ps1 spikes\sql\common_audit_store.sql -Database AW_SpikeB -Log spikes\logs\sp10-20-aw-common-audit-store.log
   .\scripts\run-sql.ps1 spikes\sql\sp10_20_aw.sql -Part 2 -Database AW_SpikeB -Log spikes\logs\sp10-20-aw-part2.log
   ```

**스크립트 수정과 재실행(2026-11-10)**

- 1차 실행: 마지막 '가장 중 다른 DB 읽기'에서 트랜잭션이 doomed(−1)가 됐다. 그 뒤 TRY 밖의 `REVERT`가 `Msg 3930 ... cannot support operations that write to the log file`로 실패해 배치가 끝났다. 결과 표가 나오지 않았다(`sp10-10-part2-run1-3930.log:7`, 배치 45행 = `REVERT;`). 이것도 측정 결과다. → REVERT를 TRY로 감싸 결과를 남기고(`revert_after_other_db`), ROLLBACK한 뒤에 아직 가장 중이면 REVERT하도록 바꿨다(`state_after_rollback`). 음성 대조도 같은 순서로 바꿨다. 판정 기준과 verdict 식은 그대로다.
- QUOTED_IDENTIFIER ON 확인: 미니 판의 모든 실행은 `run-sql.ps1`에 `-I`가 들어간 뒤(09:07:58)에 했다. 최종 실행 로그에서 모듈 4개 중 `uses_quoted_identifier = 0`은 0개다(`sp10-10-part2.log:48` `modules 4 0`). AW 판의 감사 트리거도 `uses_quoted_identifier = 1`이다(`sp10-20-aw-part2.log:49`). 정리 뒤 AW_SpikeB의 OFF 모듈은 0개다(`:129`).

### 확인한 사실

1. 열린 트랜잭션 하나 안에서 EXECUTE AS USER → DML → REVERT를 5회 반복할 수 있다. 가장 중 `USER_NAME()`은 spk_user, `@@TRANCOUNT`는 1, XACT_STATE는 1이다.
2. dbo 소유 감사 트리거는 dbo 소유 `audit.CaptureSeq`(NEXT VALUE FOR)·AuditHeader·AuditRowImage·AuditControl에 쓴다. 사용자는 이 객체에 직접 권한이 없지만(직접 읽기 229, AW `perm_spk_dml_audit spk_dml 0 0 0` `sp10-20-aw-part2.log:61`) 쓰기는 소유권 체인으로 성공한다.
3. 소유자가 다른 스키마(`auditx`, spk_owner)의 SEQUENCE에 쓰는 트리거는 DML 전용 사용자 문맥에서 229로 실패한다. 트리거 안 오류라 트랜잭션은 doomed가 된다. 감사 트리거가 사용자 문장 자체를 실패시키는 관찰자 효과다.
4. 가장 중 3부분 이름으로 다른 DB를 읽으면 916이 나고 **트랜잭션이 doomed가 된다**(문장만 실패하는 것이 아니다).
5. doomed 트랜잭션에서는 **REVERT가 3930으로 실패하고 가장이 유지된다.** TRY 밖이면 배치도 끝난다. ROLLBACK한 뒤 REVERT는 성공한다. doomed 상태에서는 가장한 사용자로 audit을 읽을 수 없으므로(229), 그 문장까지의 감사 기록은 도구 계정으로 읽기 전에 롤백으로 사라진다.
6. 감사 헤더의 `tranCount`는 BEGIN TRAN 안 문장에서 2다(미니 판, AW 판, SP6 모두 같음).
7. AW: spk_dml은 TransactionHistory INSERT·Person UPDATE·IndividualSurveySchemaCollection EXECUTE·`dbo.ufnGetAccountingStartDate`·`dbo.uspLogError` EXECUTE 권한이 없다(`sp10-20-aw-part1.log:13` `perm_spk_dml spk_dml 1 0 0 0 0 0`). 그래도 SalesOrderDetail 1행 UPDATE의 트리거 연쇄 전체가 dbo와 같은 결과를 냈다.
   - `@@ROWCOUNT` 1, 오류 없음, XACT_STATE 1(`:40`~`:45`).
   - 바뀐 테이블 4개(SOD, TransactionHistory +1행, Person.Person(xml만), SOH). 값: OrderQty 1→2, SubTotal 20565.62→22590.61, RevisionNumber 10→11, TotalPurchaseYTD −8078.66→−6053.67(`:28`~`:39`, `:46`).
   - SalesPerson·SalesTerritory는 바뀌지 않았다. 회계 기간(`ufnGetAccounting*` 2003-07-01~2004-06-30)에 든 주문이 없어서라고 본다(추정: 함수 반환값과 주문 날짜는 로그로 남기지 않았다. SP8에서 확인). dbo.ErrorLog는 0행 그대로다(`:27`).
   - 형식화 xml `.modify`, dbo 함수 호출 모두 소유권 체인으로 통과했다.
8. AW 감사 있음: 감사 기록이 dbo와 spk_dml에서 같다. 테이블·연산별 발동 수·행 수·nestLevel, 발동 순서, 이미지 11행(유효 JSON 11)이 모두 일치한다(`sp10-20-aw-part2.log:67`~`:74`).
   - SalesPerson·SalesTerritory U는 0행 발동으로 기록됐다(`:71`·`:72`).
   - Person.Person U는 6회 발동했다(`:67` `firings=6 ins=2 del=2 nest=3,3,2,3,3,2`). 6회 중 4회가 iuPerson의 0행 UPDATE다.
9. 감사 설치 DDL이 AW의 DB DDL 트리거 `ddlDatabaseTriggerLog`를 발동한다. CREATE_TRIGGER뿐 아니라 `sp_settriggerorder`도 ALTER_TRIGGER 이벤트로 출력·기록된다(`sp10-20-aw-part2.log:16` `ALTER_TRIGGER - Sales.dbr_audit_SalesOrderDetail_U`, `sp10-20-aw-part1.log:6` `GRANT_DATABASE - .Sales`). 이 행들은 AW_SpikeB의 dbo.DatabaseLog에 남는다.
10. (참고, SP3 범위) RECURSIVE_TRIGGERS OFF인 AW_SpikeB에서 uSalesOrderHeader가 자기 테이블(RevisionNumber)을 다시 갱신한 것이 감사 트리거(다른 트리거)에 nest 3, 1행으로 잡혔다. 발동 순서는 `[Sales].[SalesOrderHeader] U(3) > … > [Sales].[SalesOrderHeader] U(2)`이다(`:70`, `:74`).

### 추정

- 테이블 스키마의 소유자가 dbo가 아니면 그 스키마의 감사 트리거(트리거 소유자 = 테이블 스키마 소유자)에서 dbo 소유 audit로 가는 소유권 체인이 끊긴다. 그러면 음성 대조와 같이 DML 전용 사용자의 문장이 229로 실패할 것이다(AW는 스키마 5개 모두 dbo 소유라 실측 안 됨).
- 감사 트리거를 `WITH EXECUTE AS N'dbo'`로 만들면 소유자가 달라도 쓰기가 될 것이다(실측 아님).

### 설계 반영 제안 (오케스트레이터가 architecture.md에 반영)

1. A18·§5.2 문장 경계: 실행기는 문장이 끝나면 `XACT_STATE()`를 먼저 본다. −1이면 **ROLLBACK 뒤 REVERT**한다(REVERT 먼저 하면 3930이고 가장이 남는다). doomed 문장은 그 문장의 감사 기록을 읽을 수 없으므로 결과를 "오류 + 롤백"으로 보고한다. 롤백 뒤 남은 변경은 기준 스냅샷 비교로만 찾는다(A22와 같은 경로). 부분 전파를 보이려면 샌드박스에서만 실행 사용자에게 audit SELECT를 주는 방법이 있다(doomed에서도 읽기는 됨, 미측정).
2. A18 다른 DB 참조: 가장 중 3·4부분 이름의 다른 DB 참조는 916과 함께 트랜잭션 전체를 doomed로 만든다. 배치 분석(D5)에서 실행 전에 거부하는 것을 제안한다.
3. §13 SP10 '실패하면'은 적용하지 않는다. 대신 설치 사전 조건을 둔다: 대상 테이블 스키마의 소유자와 audit 스키마의 소유자가 같아야 한다. 다르면 C9가 그 테이블을 제외 사유로 남기거나 `WITH EXECUTE AS` 같은 대안을 실측한 뒤 쓴다. backend-3는 2026-11-10에 "실효 소유자가 dbo가 아니면 제외(`OWNER_NOT_DBO`)"를 C9에 반영했다고 보고했다. 이 스파이크에서 다시 실측하지는 않았다.
4. §6.2 `tranCount`: 샌드박스 실행에서는 2가 정상값이다.
5. §5.1 감사 설치: 설치 DDL(CREATE TRIGGER, `sp_settriggerorder`의 ALTER_TRIGGER, DROP)은 사용자 DB DDL 트리거를 발동한다. 기준 스냅샷을 설치 뒤에 만들지 않으면 DDL 트리거의 기록(AW는 dbo.DatabaseLog)이 잔차로 나온다. DDL을 막는 DDL 트리거가 있는 DB에서는 설치가 실패할 수 있다(미측정).

### 미확인

- 스키마 소유자가 dbo가 아닌 DB에서의 실제 동작, 감사 트리거 `WITH EXECUTE AS` 대안.
- 원본 사용자가 Windows 로그인·그룹, 애플리케이션 역할, 인증서 서명 모듈로 권한을 얻는 경우.
- 다른 DB로는 SpikeLab_SP10_Other를 썼다. 실제 기준 스냅샷 DB(AW_Sandbox_base) 읽기는 보지 않았다.
- AW 트리거가 오류로 CATCH(ROLLBACK + uspLogError)에 들어가는 경로는 이번 문장에서 나오지 않았다(ErrorLog 0행).
